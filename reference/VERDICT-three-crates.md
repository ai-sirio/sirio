**tiller_control**, driven from a standalone harness under `/tmp/critic3` (path-dependency on the crate, no edits inside the checkout) that starts a real `ControlServer` and attacks it as an external client:
- Half a request line then hang → the connection blocks, but a second client connects and gets a normal reply immediately (thread-per-connection isolation holds).
- A 5 MB request line (5x the 1 MiB cap) → server writes back `{"error":"request line too large"}` and closes the connection; no hang, no memory blowup.
- 4 KB of non-UTF8 binary garbage → clean `{"ok":false,"error":"malformed request: expected value..."}`, connection and server both survive, verified with a follow-up ping.
- Invalid UTF-8 bytes embedded inside an otherwise well-formed JSON line → clean `{"ok":false,"error":"malformed request: invalid unicode code point..."}`, no panic.
- 10,000 sequential requests on one connection → all answered in 362ms, no degradation, no leak.
- 200 connections that write a request and disconnect immediately (before reading the reply) → server unaffected, still answers a follow-up client.
- Two clients, one sends a half line and hangs forever, the other sends a real request concurrently → the second client's round trip completed in 6.4ms, proving the slow client never blocks it.
- A client killed abruptly mid-write (forced `SO_LINGER(0)` RST instead of a clean FIN) → server survives, still answers the next client.
- Concurrent-connection burst test (not in the assignment's list but the natural extension of "ten thousand requests"): a barrier-synchronized simultaneous connect of N clients. n=64/128/200/300 → 100% succeed. n=500 → 471/500 succeed, 29 fail with a real `ECONNREFUSED`-class connect error. `sysctl kern.ipc.somaxconn` on this machine = 128; the accept loop is a non-blocking `listener.accept()` polled every 5ms (`POLL_INTERVAL`), and once a connection burst outruns what that poll cadence can drain, the OS backlog fills and further connects are refused outright — Unix domain sockets do not silently queue past the backlog the way some assume. Real-world impact is low (Tiller's actual client population is one app plus a handful of hook subprocesses, not hundreds of simultaneous connects), but it is a real, measured ceiling.
- **Socket permission race — the serious finding.** I wrote a tight polling loop that stats the socket path in a spin from another thread while `ControlServer::start()` runs (bind → `chmod 0o600` → post-bind owner/type sanity check). Over 500 trials: 488 caught the file at mode `0755` (the umask-derived mode `UnixListener::bind` leaves it at before the crate's own `chmod` call locks it down). I then went further and proved this is exploitable, not just observable: a second thread racing a real `UnixStream::connect()` against the same startup window succeeded on the very first attempt, and the connection it captured — established purely by winning the pre-chmod race — remained fully live and authorized *after* `start()` had returned (chmod done, sanity check passed): I sent a real `system.ping` over it and got back `{"id":"race","ok":true,"result":{}}`. Any other local user's process, if it is polling for the socket path at the moment Tiller's control server (re)binds — app launch, or a stale-socket takeover — can win this race essentially every time and keep a persistent, fully-authorized channel to drive Tiller (`notify`, `workspace.create`, anything the protocol exposes) indefinitely, immune to the very chmod that was supposed to be the privilege boundary. This is exactly the "anything that lets another user on the machine drive Tiller" case the assignment asked me to check for, and it is real.
- `client.rs`'s response-read loop (used by `round_trip`, i.e. `tillerctl` and every test) has no cap on the accumulated response buffer, unlike the server's `MAX_BUFFER_BYTES` — a misbehaving or compromised server sending an unterminated giant line would grow the client's memory unbounded until the (very long, 3600s default) read timeout fires. Lower severity since it is a local, normally-trusted peer, but it is an asymmetry: the crate hardens the direction it expects hostility from and not the other.

**tiller_activity**, driven from the same harness against a real `AgentActivityModel`:
- Bare braille spinner (`⠋` alone, no name text) → `identify_agent_from_title` returns `None`, confirmed — correctly refuses to pick between Claude and Codex, both of which animate the same glyph range.
- `"π - tiller"` → `Some("pi")`; `"π: tiller"` → `Some("omp")` — confirmed the colon is read as the sole distinguishing mark, resolving to different agents from otherwise near-identical titles.
- Layer D (`process_identified`) claims a pane as `"claude"`, then a Codex-shaped title (`"codex - thinking"`) arrives for the same pane → identity stays `"claude"`, `is_process_owned` stays `true`, no transition fires. Process ownership correctly resists an unrelated, conflicting title, per the spec's ownership rules.
- `process_gone` on a pane that is *not* process-owned (a spawn-owned pane registered via `agent_spawned`) → confirmed no-op; the spawn-owned pane's `Running` status survives untouched. Ownership boundaries hold in both directions.
- A process-owned pane's process disappears (`process_gone`) → status and identity both clear; a fresh title arriving afterward for the same pane id correctly re-identifies it as a brand-new, title-owned pane rather than resurrecting the old one.
- Layer C content signal applied immediately after spawn, with no debounce check → applies unconditionally as documented (content is deliberately not gated by the Layer-A debounce window).
- **The real gap I found**: `AgentActivityModel::notify` (Layer A) takes a caller-supplied `now: Instant` and has no check that it is not older than the pane's last recorded update. Demonstrated directly: `notify(pane, Done, t_new)` followed by `notify(pane, Running, t_old)` where `t_old` is a full second *before* `t_new` — the model's status for that pane regresses from `Done` back to `Running`, driven purely by an older timestamp arriving later. `tiller_control`'s server spawns one OS thread per connection with no cross-connection ordering guarantee, so two rapid hook calls for the same pane (entirely plausible from a real agent's lifecycle hooks firing close together) can reach the model out of order, and nothing in either crate defends against it. The result is a genuine, reachable status-flicker/regression bug, not merely a theoretical one — this is precisely the "clocks going backwards" scenario the assignment asked me to probe for.

**tiller_markdown**, driven from the same harness plus a purpose-built bisection binary:
- A ~3.2 MB realistic document (20,000 headed sections with prose, a list, and a fenced code block each) → parses in 35-95ms across runs, 80,000 top-level blocks, no issue.
- A fence opened and never closed at the very end of a 500,045-byte prefix → parsed in 2.6ms, the last code block correctly reports `open: true`.
- A table with ragged rows (a 3-column header against rows of 2, 5, and 1 cells) → no crash; every row reports 3 cells (pulldown_cmark pads/truncates to the header width, and the crate passes that straight through).
- Invalid UTF-8 boundaries: the public API takes `&str`, so I drove the realistic failure mode directly — a byte buffer sliced at every possible cut point of a string containing an emoji and an em-dash, converted with `str::from_utf8` the way a real streaming caller would. 5 of 63 cut points landed mid-codepoint and were correctly rejected *before* ever reaching the parser; the other 58 valid prefixes all parsed without incident. This means UTF-8 safety at the streaming boundary is the caller's job by construction (a defensible contract, but worth naming: the crate itself does no byte-level validation).
- Byte-at-a-time re-parse timing on a realistic 8 KB reply (8,072 re-parses, one per byte) → worst single re-parse 115µs, average 37.6µs, nowhere close to a 16ms frame budget. A separate scaling probe on single full parses at 8 KB / 32 KB / 64 KB / 128 KB / 256 KB / 512 KB / 1 MB showed roughly linear cost (62µs → 7.2ms), confirming the crate's own doc comment is accurate: a single parse is cheap, and the real cost is the *sum* of re-parsing a growing prefix over the life of a long streaming reply, which the crate honestly documents and explicitly recommends throttling for. Not a hidden defect — a stated, quantifiably-accurate tradeoff.
- **The real, serious finding**: `parse_with_options` recurses through `parse_block` → `parse_blocks` (for block quotes) and through `parse_inlines` (for emphasis/strong/links/images) with no depth limit, one stack frame per nesting level. I bisected the exact crash threshold using nested blockquote markers on a single line (`"> " × depth`, chosen specifically so total input size grows linearly with depth, isolating recursion depth from sheer byte volume): depth 8,000 parses in 2.8ms with no issue; depth 9,000 and every depth tried above it (10,000 / 11,000 / 12,000 / 15,000 / 25,000 / 40,000 / 60,000 / 100,000) reliably crashes the whole process — `thread 'main' has overflowed its stack / fatal runtime error: stack overflow, aborting`, exit code 134 (SIGABRT). This is **not** a catchable panic: `std::panic::catch_unwind` does nothing for a real stack overflow, confirmed directly (the wrapped probe still took the process down). A ~18 KB single line of `"> "` repeated 9,000 times is trivially within what a real (or adversarial, or simply buggy) assistant reply could contain, and this crate's own stated purpose is parsing exactly that: untrusted, streaming assistant markdown. Whatever thread calls `tiller_markdown::parse` on a real reply — almost certainly the render/main thread of the chat UI — goes down with it. Recursive `Drop` on a successfully-parsed deep tree was also checked (a depth-3,000 tree, safely below the crash line, dropped in 167µs with no issue), so both the parse-time and drop-time recursion are structurally the same risk, just with parse recursing first and hitting the ceiling before a document ever gets deep enough to make drop the bottleneck.

BIGGEST GAP: `tiller_markdown::parse` has no recursion-depth limit, so a single realistic-sized streamed reply containing ~9,000+ levels of nested markdown structure (blockquotes, lists, or emphasis — anything the recursive-descent builder walks per nesting level) reliably stack-overflows and aborts the entire Tiller process with no catchable error, and this is reachable purely from untrusted assistant output with no timing, privilege, or attacker co-residency required — strictly more severe and more directly reachable than the control-socket permission race (which needs a local attacker racing app startup) or the activity clock-ordering bug (which degrades a status badge, not the process).
