**Launch / send / exit / status-follows-exit — PASSED, live.** Command palette → typed

a "Process exited successfully" banner appeared (`/tmp/recensus0818n-shots/14-after-ctrlc3.png`).
`OpenCodeAdapter::has_native_hooks` returns `false` (`rust/crates/tiller_agents/src/opencode.rs:44-46`)
and the adapter never calls `tillerctl notify`, so this status transition is necessarily
process-exit-driven, not hook-driven — exactly the clause's "status follows process exit rather
than hook notifications."

**Resume by session reference — FAILED, live, real wiring gap (not an environment limit).**
Reused the same DB across two separate app launches (`TILLER_WL_LABEL=recensusresume`, same
`/tmp/recensusresume.sqlite`, per `wayland-drive.sh`'s `TILLER_DB="$DB"`). Run 1: created the
OpenCode pane, sent a message, confirmed a session ref was recorded
(`ctl session.transcript session=pane-2 agent=opencode worktree=…` → `"session.transcript has no
reader for agent 'opencode'"` — this specific error text only fires *after*
`session_refs.get(pane_id)` succeeds, at `rust/crates/tiller/src/main.rs:1897-1919`; the
alternative error, `"no session reference recorded for this pane"`, would have fired instead if no
ref had landed — so this is a positive, not a negative, result), then exited via Ctrl+C. Run 2:
fresh boot against the same DB. `ctl panel.list` showed the OpenCode tab auto-restored
(`pane-2`/`OpenCode`), but its terminal ran a **plain interactive bash shell**, never `opencode` at
all — `ctl panel.scrollback id=pane-2` decoded to a fastfetch banner + bash prompt only, no
opencode output, no error text (`/tmp/recensusresume-shots3/`). Read the DB directly
(`python3 -c "sqlite3 … select * from tab"`): the `tab` row for this pane has `agent_id = NULL`.

**Root cause, named:** `add_agent_tab` (`rust/crates/tiller/src/main.rs:6531-6569`) calls
`self.add_terminal_tab_with_shell(...)` (→ `insert_terminal_tab`,
`rust/crates/tiller/src/main.rs:6006-6034`), which pushes the new `OpenTab` with
`agent_id: None` (line 6021) and *immediately* calls `self.schedule_save(cx)` (line 6032).
`schedule_save` (`main.rs:3606-3608`) evaluates `self.layout(cx)` **eagerly**, synchronously, as
the argument to `self.session.schedule(...)` — so the `SessionLayout` snapshot handed to the
(debounced) writer already has `agent_id: None` baked in. Only after this does `add_agent_tab`
set `tab.agent_id = Some(adapter.id())` (line 6567) — one line too late, and `schedule_save` is
never called again with the corrected value. `session_ref` persistence is unaffected (it is
written through a separate table, `session_ref`, from the control-socket handler), which is why
the session ref survived the restart but the agent identity that would let `restored_agent_shell`
(`main.rs:10033-10058`) pick `adapter.resume_command(...)` did not.

**The single concrete fix a builder must add:** in `add_agent_tab`
(`rust/crates/tiller/src/main.rs:6567`, right after `tab.agent_id = Some(adapter.id().to_string())`),
call `self.schedule_save(cx)` again — or, cleaner, thread `agent_id` into
`insert_terminal_tab`/`add_terminal_tab_with_shell` so the very first (and only) `schedule_save`
call already carries the correct value.

**Verdict:** half-proven — launch/send/exit/status-follows-exit fully proven live; resume-by-ref
fully attempted live and found broken by a one-line ordering bug, not by any environment gap.
