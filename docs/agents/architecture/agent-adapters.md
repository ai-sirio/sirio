# Agent adapters (`sirio_agents`)

Every supported CLI implements the `AgentAdapter` trait (`id`, `display_name`, `has_native_hooks`, `prepare`, `command`, `resume_command`). `sirio_agents::ALL` is the fixed list of 5 adapters, in display order. An adapter's ACP claim (`builtin_acp`) covers only its own binary's subcommand — verified, defaulting to `None`; everything reachable through a separate package resolves through `sirio_registry`. `prepare` writes only worktree-local files, its hook config and the skill, and **never** touches user-global config (`~/.claude/settings.json`, `~/.codex/config.toml`, etc.). The writers outside Sirio's own data are explicit buttons and four startup steps (the third is OpenCode's, below; the fourth is the IDE bridge's, below), never a pane. Settings → General → **Install Hooks** (`install_global_hooks`, a trait method defaulting to `NotSupported`) writes the hooks: Claude merges the five hook arrays into `$CLAUDE_CONFIG_DIR`/`~/.claude/settings.json`, Codex sets `notify` in `$CODEX_HOME`/`~/.codex/config.toml` via `toml_edit` (format-preserving), OpenCode writes `~/.config/opencode/plugins/sirio-session.js` only for a confirmed OpenCode 1.x (the verdict is the major version `opencode --version` reports, run in the selected worktree, never the service registration; under 2.x, and when the binary gives no readable version, it writes none and removes the file only when it is Sirio's own generated global plugin, naming the path in the report; any other file there is left byte for byte; under no readable version the report says `OpenCode: no hook needed — OpenCode did not report its version, so no plugin was written`; the version memo never unlearns a version read earlier in the run, so a slow or failed probe changes nothing). "Sirio's own generated file" means exactly the generated text: the template of `sirio_agents/src/opencode.rs` (`PLUGIN_TEMPLATE` for the worktree file, `GLOBAL_PLUGIN_TEMPLATE` for the global one, and `LEGACY_PANE_PLUGIN_TEMPLATE`, the worktree text older builds wrote, which named one pane) with `__SIRIOCTL__` replaced by a one-line JSON string literal and, in the legacy text, `__PANE__` by `pane-<digits>`, every other byte equal; a file with Sirio's header line and anything else is the user's and is left byte for byte. A file an older build wrote in any other shape is not recognised, so it stays. The startup step: when the app's version probe reads 2 or more, it removes Sirio's generated global plugin (the same exact match), because OpenCode 2 refuses it and no button would take it away, and logs `[sirio] opencode: removed Sirio's generated global plugin (OpenCode 2 refuses it)`; Pi and omp honestly report no user-global mechanism. Those hooks carry **no** `--session`: `sirioctl notify`/`session-ref` fall back to the `SIRIO_PANE_ID` every Sirio pane exports and exit 0 silently outside one (no pane, or no socket), so a global hook never surfaces an error inside an agent Sirio did not launch. Adapters that generate command-line overrides embedding JSON (Codex's `-c notify=[...]`, omp's hook file) share `json_string_literal` in `sirio_agents/src/shell_quote.rs` — it must build a JSON string literal without escaping slashes, because Codex's `-c key=value` override is parsed as **TOML**, and `\/` (JSON's optional slash-escaping) is not a valid TOML escape. Getting this wrong makes Codex fail silently at config load, before it ever reaches its TUI. OpenCode's session ref, the id a relaunch resumes with (`opencode --session <ref>`), has two sources, decided by the binary's `opencode --version` (`sirio_agents::opencode`, memoized for the process: probed off the UI thread, in the folder the pane runs in so that a version manager's per-folder choice (mise, asdf) is the pane's, at startup, at each fresh OpenCode tab and at Install Hooks; a restored OpenCode pane waits for the first probe, and a fresh tab decides on its own probe's answer). Never by `service.json`. OpenCode 1.x: `prepare` writes the worktree-local plugin `.opencode/plugin/sirio-session.js`, which reports the id through `sirioctl session-ref`; it names no pane, one file serves every OpenCode tab of the worktree, so it reads the pane from the `SIRIO_PANE_ID` of the `opencode` process that loads it (and reports nothing without one). OpenCode 2.x (or later), or no readable version: `prepare` writes no plugin and removes `.opencode/plugin/sirio-session.js` only when it is Sirio's generated one (the exact text, the current one or the legacy one that names a pane, `LEGACY_PANE_PLUGIN_TEMPLATE`) (OpenCode 2's TUI shows "Plugin failed" for it); a fresh tab then reads `$XDG_STATE_HOME/opencode/service.json`, checks `GET /api/info` (the pid matches, the major is 2 or more) and sends `POST /api/session` with `{"location":{"directory":<the tab's worktree>}}`, all within one 3 s deadline off the UI thread. With the reply's id Sirio writes it as the pane's ref and launches `opencode --session <id>` (plus `--prompt` for a hand-off). Any failure (v1, no answer, service down, non-200, timeout, a reply for another directory) launches plain `opencode` with no ref. Titles write no ref at all: a typed `opencode` has none. A fresh terminal tab deletes the row under the key it takes (the code deletes for every new terminal tab, plain and Show included; it looks in the app's in-memory copy of the rows, every row loaded at startup or written through the app since, and touches the database only when that copy has one, so the common tab open writes nothing from the UI thread, and a row another connection writes while the app runs is not seen), for every agent, because a pane id is reused and a stale row would resume in the new pane; an OpenCode 2 tab saves its created session under its key only when no other session names that key, and otherwise deletes the row there, so that a tab running `--session <id>` never keeps another pane's row. The tab is found wherever it is held when the creation step ends: a fresh OpenCode 2 tab whose session is created while a worktree switch has parked it launches `opencode --session <id>` and saves its ref under its own key as an active tab does (the held-by-other rule applies, comparing the persistence id and the worktree, since default tabs of different worktrees share persistence ids). A tab whose worktree is evicted while the step runs still exists (eviction only detaches: its view keeps its link, and the restored tab attaches to the session it opens), so it launches `opencode --session <id>` too, with its prompt, but no ref is written, since no strip says which key it holds. A tab closed before the step ends (or detached by a quit, best effort) gets nothing launched and no ref, and Sirio deletes the session it created through `DELETE /api/session/<id>` (one 3 s deadline; the log names kinds only, never the id; measured on 2.3.0: 204 for a held session, then 404 `SessionNotFoundError`). For every agent, the first launch of a tab sends the tab's first prompt (a hand-off's) and every later open of the tab (Restart from the context menu or the *Session lost* overlay, a reopen after a pane-id move) runs the same command without it (`TerminalView::set_relaunch_shell`); an OpenCode 2 tab resumes `--session <id>` without `--prompt`. A retry after the id was taken never ran a session, so it still sends the prompt. The first launch counts as done once its session started on the host, not once the agent read the prompt: an agent that fails at once (missing from the PATH, a crash at start) has used its prompt, and a Restart runs it without; a host that dies after starting the process but before answering leaves the launch not done, so the Retry sends the prompt again. Limits: the ref does not follow switches made inside the TUI (`/new`, `/sessions`, its tabs), it stays on the session Sirio created; after a reboot the service is down, so the first OpenCode tab launches plain and gets no ref (that `opencode` starts the service); a session the user never prompts in stays behind, empty and untitled; a session created after the 3 s deadline is still left behind, and a tab whose worktree is evicted during the step runs its session with no ref, so once that process ends the tab resumes nothing (no end-to-end case covers eviction); an id several layouts name, while no dedup has run (the host has not answered in this run), can still get a row written by one worktree's live pane and resumed by the other's restore if that first worktree is no longer parked at the switch (the exception to the ambiguous-row rule below: the startup purge sees only the rows there at startup); a restored OpenCode 2 tab that a pane-id move gives a new id starts plain `opencode` and has no ref from then on, since OpenCode 2 reports none; the version memo is one per process, so worktrees pinned to different OpenCode majors are told apart only by a fresh tab's own probe; restored OpenCode panes wait for the startup probe (75 ms on 2.3.0, at most 5 s), those whose session the host still runs included. Codex, pi, opencode and omp `prepare` write `.agents/skills/sirio/SKILL.md` in the worktree, from the copy the binary ships, and the app keeps that file out of git through the common dir's `info/exclude` (`keep_agent_skill_out_of_git` in `sirio/src/main.rs`, for `SHARED_SKILL_ADAPTERS`); Claude writes `.claude/skills/sirio/SKILL.md`, and that folder is not excluded. The skill is no longer installed with `npx`. **Install Skill** writes the user-level copy for each CLI, at the paths `sirio_agents::user_skill_paths` names: `<CLAUDE_CONFIG_DIR or ~/.claude>/skills/sirio/SKILL.md`, `~/.agents/skills/sirio/SKILL.md` (Codex, Pi and Oh-My-Pi read it together) and `<XDG_CONFIG_HOME or ~/.config>/opencode/skills/sirio/SKILL.md`; a file without the managed marker is never replaced. The startup refresh rewrites only a copy Sirio already wrote, and only when it differs from the bundled skill; a debug build runs it only with `SIRIO_CLI_AS_RELEASE=1` (`cli_install::stable_is_debug`). The fourth startup step is the IDE bridge's lockfile, `<home>/.claude/ide/<port>.lock` (only the file named by the port this Sirio bound; removed on quit and when the switch is off; see [IDE bridge](ide-bridge.md)), and its environment: while the switch (`claude.ideBridge`, default on) is on, every new terminal gets `CLAUDE_CODE_SSE_PORT=<port>`, fixed at the session's creation like the rest of `worktree_environment_in`; `ENABLE_IDE_INTEGRATION` is never set (Claude does not read it); and the name is in `sirio_env::PER_PANE`, so a Sirio launched from a VS Code terminal never hands that terminal's port to its panes and the native chat never inherits one. A pane's session ref (the id a relaunch resumes with) has a life cycle of its own. The ref row goes when its tab, pane, worktree or project is closed and when any new terminal tab takes its key (the fresh-tab rule above), for every agent; quitting, restarting a terminal and evicting a worktree keep it. Pane ids are not unique across layouts, and a row under a key two layouts hold may be either pane's, so such a row is deleted, never kept for the other layout: losing a resume is acceptable, a wrong one is not. For the same reason each of the three pane-id moves (the dedup, a rebind on `IdTaken`, the rename when a worktree is selected) clears both keys of every pane it moves and copies nothing, for every agent (an OpenCode 2 tab opened in this run then saves the session Sirio created for it under the new key: that id is its own launch, not a row read under the old key), because the old id is by construction held by another session (another layout, a live host session on `IdTaken`, a parked pane), and the new key may carry a row an older build never deleted. A dedup run late (at the host's first answer after a startup it missed) clears the old key too, though a live pane may hold it: a second live writer under the id may have written the row. There is no legacy fallback key. At startup, before any tab restores, every row whose reference two or more keys hold is deleted (an older build's worktree-local hook file named one pane for every tab of the worktree, so two tabs could hold one conversation; a lone row under the wrong key is not detectable and stays), then the row under every pane id that two or more worktrees' saved layouts name, and a restore that hands a tab a fresh id first deletes the row under it, as a fresh tab does. A key closed in this run refuses later ref writes that arrive over the control socket (hooks, `sirioctl session-ref`, `sirioctl notify --agent-session`), and Sirio's own save of an OpenCode 2 tab's created session the same way: nothing is written and the app logs `[sirio] pane-N: session ref not written: its pane was closed`. Claude's `SessionEnd` hook (`sirioctl notify --status done --stdin-json`, which carries the session id) lands after the close deleted the row and would write it back, and the next pane to get that id after a relaunch would resume the closed conversation. The mark lives for the run: the allocator only grows, so within a run it never hands a marked key out again, and only a restore that hands the key to a pane again lifts a mark (a worktree closed and selected again in the run, or another worktree whose layout names the same legacy id); freeing a key does not. Closing a tab or pane that only shows an attached session (Show session, an orphan of another worktree shown in the active one because that worktree has no saved layout) detaches it and neither ends nor deletes its ref: the session lives on, and a fresh tab that gets that id deletes the row as it is made. The cost: a pane id two layouts hold (including a layout restored with duplicate ids when the startup dedup did not run) loses that pane's reported writes for the rest of the run: its resume, `system.identify` and `session.transcript`. The worktree-local hook files name no pane, because one worktree holds one such file for all of its tabs of an agent (a pane named there would be every tab's, the last one prepared, and an explicit `--session` beats the environment, so one tab's session id would land in another's row): `.claude/settings.local.json` runs `sirioctl notify --status <s> --stdin-json`, `.sirio/omp-hook.ts` reads `process.env.SIRIO_PANE_ID` (and skips when it is empty) and `.opencode/plugin/sirio-session.js` reports only when `SIRIO_PANE_ID` is set, so each agent process's own `SIRIO_PANE_ID` names its pane.
