Change requests grow up: you can now merge, review, re-run CI and hand a
pull request to an agent without leaving Sirio. Sirio also starts a small
background process, the host, which later releases build on.

**Change requests, end to end**

The right panel's Change requests list and the tab that opens from it are
redrawn with Ely, and they now do the work as well as show it.

- **Merge.** A bar under the header says whether the change request is ready,
  waiting, still being checked or blocked, and why. Merge, auto-merge and
  deleting the branch are one confirmation away, and Sirio refuses the merge
  if the head moved since you looked. Reviewers and labels are edited from
  the tab and sent when the picker closes.
- **CI.** Re-run a job, or re-run only the failed ones. A job's log opens in
  its own read-only tab, coloured and foldable, and a running job's log keeps
  reloading while you look at it.
- **Review threads.** The *Files* diff shows the forge's threads under the
  lines they belong to, and the Conversation lists one entry per thread.
  Outdated threads fold into a section of their own. You can reply to a
  thread, resolve or reopen it, comment on a line or a range from the diff's
  gutter, and edit your own comments.
- **Reviews.** Start a review from a line comment or a reply, add to it, edit
  or delete what is pending, then submit it with a verdict or discard it. On
  GitHub that is the pending review; on GitLab it is the draft notes.
  *Suggest* inserts a suggestion block, and a suggestion you receive is drawn
  as a small diff. Applying it stays on the forge.
- **The list and the Changes tab.** Both are redrawn with Ely: filters as
  icon tabs, search behind a button, skeletons while loading. Discard in the
  Changes tab now asks inside the window instead of with a system prompt.

**From a change request to a worktree**

*Open in a worktree* brings the branch of a pull request or merge request
into a worktree that pushes back to it. A fork's branch gets a remote of its
own, so a plain `git push` from its worktree reaches that fork and nothing
else. An existing worktree is fast-forwarded only when it is clean and on
that branch; otherwise it is left alone and the status line says why.

**Hand it to an agent**

*Hand off to an agent* (in the tab's action bar and the list row's menu),
*Fix with agent* on a review thread and on a failed check open one dialog:

- **What for:** fix the review comments, fix failing CI, review, or resume
  the work.
- **Which agent:** any of the five, or none.
- **Where:** a terminal or a chat.

Sirio reads what that needs from the forge before touching git, checks the
change request out, writes a context file under `.sirio/handoff/` in the
worktree (kept out of git), and starts the agent on it. Everything the forge
wrote, such as comments, names and logs, is fenced as untrusted text in that
file, and the agent is told so.

**The host**

Sirio now starts `sirio-host`, a small process detached from the app, and
adopts it on the next start. It does not run anything yet: your terminals
and chats behave exactly as before, and without the host the app runs as it
always did. It is the foundation for agents that survive a crash, a Force
Quit or an update. Its status is shown in Settings → General.

**The chat**

The bar above the chat that named the agent, the model and whether it was
working is gone. The agent and model are still in the row under the
composer.
