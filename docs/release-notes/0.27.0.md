Sirio now shows your GitHub pull requests and GitLab merge requests: a list
in the right-hand panel, and each one in a tab of its own. On macOS the
Permissions page reads the real state of each permission. A working agent no
longer lights up every worktree in the sidebar.

**Pull and merge requests in the right-hand panel**

The right-hand panel gains a fifth view, behind the pull request icon at the
end of its row of icons. It appears in git projects and works with
github.com, GitHub Enterprise Server, gitlab.com and self-managed GitLab.
Sirio asks the forge nothing until you first open the view.

At the top, a This worktree card shows the pull or merge request whose
branch is the worktree's own: its state, how far its CI has got, its review
state and its comment count. A click opens it. When the branch has none, the
card says so and offers Create on the forge, which opens the forge's
creation page in your browser.

Below the card, four filters sit side by side as icons:

- **Mine**: the ones you opened or are assigned to.
- **To review**: the ones waiting on your review, with their count beside
  the icon.
- **All open**: every open one, most recently updated first. This is where
  the view starts.
- **Closed & merged**.

Each row shows the title, the number, the author and how long ago it
changed, with its CI, its review state and its comment count on the right.
Right-click a row for Open in browser and Copy link. The search button
searches on the forge itself. Rows arrive 50 at a time, with Load more at
the end. The list refreshes when you show it and every minute while it
stays visible, and never while it is hidden.

**A pull or merge request opens in a tab**

Clicking one opens it in a tab in the right-hand pane. The header carries
its title and number, its state, its author, which branch merges into
which, and Open in browser. Below it are four tabs, as on the forges:

- **Conversation**: the description, drawn like the Markdown preview, then
  the comments, the reviews with their outcome, and events such as pushed
  commits, review requests and merges. A comment on a line names its file and line. Images in the
  description show as links, since Sirio does not load remote images.
- **Commits**: a click opens the commit in Changes when it is in your
  repository, and on the forge otherwise. Nothing is fetched.
- **Checks**: failed checks first, then running and queued ones. The rest
  fold into one row you can expand. A click opens the check's log on the
  forge.
- **Files**: each changed file with its additions and deletions. A click
  opens the changes on the forge.

While its CI is running the tab refreshes every minute. Opening one that is
already open in the worktree switches to its tab. The tab stays in the
right-hand pane, and a restart brings it back.

Sirio only reads. Commenting, approving and merging still happen on the
forge.

**Signing in to a forge**

Sirio works out each host on its own. It knows github.com and gitlab.com by
name, uses a `gh` or `glab` you are already logged in with, uses a token you
saved, and recognises GitHub Enterprise Server because it answers for
itself. For any other host the view asks whether it is GitHub Enterprise or
GitLab, and remembers the answer.

When a host has no way in, the view shows the `gh auth login` or `glab auth
login` command to copy, and a field to paste a personal access token
instead. A token needs read access to pull requests, checks and metadata on
GitHub, and the `read_api` scope on GitLab.

Settings → Git Hosting lists each host Sirio has seen, with its forge, how
Sirio signs in and the account it signs in as. For each one you can let
Sirio detect the way in, or choose the CLI or a token. A saved token is
checked against the forge before it is kept, and Forget token removes it.
Tokens go in Sirio's credential file, never in the settings. It is a plain
file in your user's data directory, not the system keychain.

A few more things about how it talks to a forge:

- Connections made with a token trust the certificates your system trusts,
  so a self-managed forge behind a company certificate authority works once
  that authority is installed. If it is not, the error says so.
- An older self-managed GitLab works with less detail. CI shows that it is
  running but not how far it has got, and a review that asks for changes is
  not told apart.
- When a forge rate-limits Sirio, the list says when it will try again and
  asks nothing until then.

**The macOS permissions page tells the truth**

Settings → Permissions listed Notifications, Screen Recording,
Accessibility, Full Disk Access, Automation and Local Network, but every
status on it was fixed text and no button did anything. Each row now shows
the real state: granted, denied, not requested, or check manually where
macOS gives no answer. The page reads them again when it opens, when you
press Refresh, and when you come back to Sirio from System Settings. Each
row has one button:

- **Request** shows macOS's prompt for a permission Sirio has never asked
  for.
- **Trigger Prompt** does the same for Automation and Local Network, which
  macOS only asks about on first use.
- **Open Settings** opens the right page of System Settings, for a
  permission already decided and for Full Disk Access.

Sirio still asks for nothing at startup.

Once you allow Sirio's notifications, they come from Sirio itself, with its
icon, and appear even while Sirio is in front. Until then they go through
Script Editor, as before. If you deny them, Sirio shows none.

**Smaller changes**

- **One working agent no longer lights up every worktree.** Since 0.26.0 a
  worktree you switched away from keeps its running mark, but worktrees
  could share one agent's status, so one busy agent marked every worktree
  in the sidebar as running. Each worktree now shows only its own agents.
- **The Markdown preview scrolls sideways in a narrow pane**, rather than
  squeezing the text into a narrow strip. A wide pane still centres it. The
  last lines of a long preview, and the bottom of its scrollbar, were cut
  off below the pane. They can now be reached.
- **The + after the back and forward arrows in the title bar is gone.** It
  never did anything. New tabs come from the + in the tab strip.
